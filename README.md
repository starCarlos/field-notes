# Field Notes

> 16 篇实操记录。全部来自真实踩坑，每篇都写清：**现象 → 我以为是什么 → 实际是什么 → 怎么定位 → 修法 → 数字 → 能拿走什么。**

## 为什么值得看

判断标准只有一条：

> **这篇东西，AI 能不能凭现有语料编出来？**

能编的（教程、概念、API 用法）不写——那些 AI 写得比人全，也比我快。
写的是编不出来的：具体的报错、失败的那几次、前后对比的数字。

所以这些不是教程，是**排查记录**。

教程告诉你「应该怎么做」；排查记录告诉你「我试了什么，不行」。

## 能反复拿走的几条

1. **同一请求在不同客户端表现不同，先怀疑客户端，别怀疑网络。**
2. **端口别信配置文件，先验一次。**
3. **一次性任务绕过优于修根因；长期服务反过来。** 判据是「这个坑还会不会再来」。
4. **`check=True` 不够，还要验内容。** 代理的错误页也是 200。
5. **「禁用」不等于「不运行」。** 一条路径关了，还有四条。
6. **量之前先问口径。** 工作集和 footprint 能差 8 倍；同一个数换个口径，能差一个数量级。

## 关于这些记录

- 全部基于个人环境实测，版本号写在文内；版本一升级，具体数字就旧了。
- 凡是来自工作场景的部分，只保留**可迁移的工程方法**；具体项目、客户、内网、内部流程一律不写。这份约束不总是做得到——**发现够线的内容，会直接删掉，不留备注。**
- **半成品会标注「根因未定位」**，不假装已经查清。有些坑的根因不值得挖，但这不代表可以写成「已解决」。
