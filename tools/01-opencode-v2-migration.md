# 配置迁移完才发现：模型没设 limit，一直在用兜底值

> 存档 ｜ 素材日期 2026-11-20 ｜ 来源：个人实测记录
> 四问：AI 编得出吗？编不出，V1 字段在 V2 里静默失效这件事只有对过文档才知道 / 有试错过程吗？有，先补 limit、再发现大半配置是旧语法 / 有数字或可复现报错吗？有，200k/32k 兜底、1M/393k 真实值 / 半年后还有人踩吗？会，所有从 V1 升上来的配置都踩

## 现象

我问了一个很普通的问题：每个模型的上下文长度限制有没有设置？

答案是没有。当时正在用的那个模型没写 `limit`，于是落到了兜底的 200k 输入 / 32k 输出。

后果不是「稍微小一点」：

- 上下文压缩点比实际能力**提前约 5 倍**
- 长输出被截到 32k

当时的体感是「这模型长文理解一般、写长东西老断」。其实模型没问题，是配置给它套了个小一号的笼子。

更麻烦的是第二层：`compaction` 里配的 `prune` / `reserved` / `tail_turns` 是 V1 字段，V2 不认。三个调参旋钮一直是空转的，调了跟没调一样。

## 我以为是 X

- 以为上下文短是模型本身上限低
- 以为压缩策略调得不够狠，想再压一压
- 以为输出被截是任务写得不清楚

三条全错，而且都错在同一类地方：**我把「配置生效了」当成了默认前提。**

## 实际是 Y

两个独立的问题叠在一起。

**一、没设 limit 就是兜底值，而且是静默生效的。** 不写不报错，只是给你 200k / 32k。这个兜底比真实上限小一个数量级——真实值是 1048576 / 393216。

**二、配置写的是 V1 语法，V2 只认一半。** 不认识的那些字段不报错、不警告，直接忽略。所以「我配了」和「它生效了」是两件事。

这两条加起来就是最难查的一类故障：不崩、不报错、只是表现比预期差。

## 怎么定位到的

顺手去翻了 V2 的迁移文档，逐个字段对了一遍。对完发现不是补一个 `limit` 的事，是整个文件的语法都该换。

对出来的映射（只列结构，不贴实际配置）：

| V1 | V2 |
|---|---|
| `provider` | `providers` |
| provider 的 `npm` | `package: aisdk:*` |
| provider 的 `options` | 拆成 `settings` / `headers` |
| `setCacheKey` | `compatibility.supportsPromptCacheKey` |
| `agent` | `agents` |
| agent 的 `reasoningEffort` | 模型 `variants` + `model#variant` |
| 模型 `modalities` | `capabilities` |
| 模型级 `options` | `settings` |
| `attachment` | `media` |
| `skills.paths` | `skills` 数组 |
| `small_model` | `agents.title.model` |
| `compaction` 的 `reserved` | `buffer` |
| `compaction` 的 `tail_turns` | 直接丢弃 |

`compaction` 迁移后只剩三项：`auto`、`keep.tokens`、`buffer`。原来的 `reserved 20000` 改成 `buffer 20000`，`tail_turns` 没有对应物。

## 怎么做的

顺序是：先备份，再迁移，最后用脚本比对，不靠肉眼看。

1. 备份原配置，文件名带时间戳。
2. 写一个一次性迁移脚本，按上表逐字段换。
3. 写一个对比脚本，按「模型 / agent / 凭据 / 地址 / 请求头 / 多模态 / reasoning」逐项比对迁移前后的语义等价。**这一步是关键**——29 个模型、5 个 agent，人眼扫一遍必漏。
4. 补 `limit`。取值不看直觉，看同类模型的共识区间：
   - 主力模型：1048576 / 393216
   - 一档 1M 上下文的模型：1000000 / 128000
   - 一个文档里查不到的 ID：272000 / 128000，按同 provider 同代模型对齐，**这是假设，不是事实**
5. 输出比对结果，确认无差异再收工。

对比脚本最后输出 `problems: none`。

## 结论

- **兜底值是陷阱。** 没配 ≠ 没限制，而是配了一个你不知道的小值。凡是「上下文不够用」的体感，先查 limit。
- **静默失效比报错危险。** V1 字段在 V2 里不报错，只是不生效。迁移时最该问的不是「改对了吗」，是「有哪个字段被忽略了」。
- **迁移必须有对比脚本。** 逐项比语义，不逐项看文件。29 个模型靠肉眼等于没检查。

## 能拿走的 4 条

1. **先查 limit，再怪模型。** 上下文不够、输出被截，八成是配置问题，不是能力问题。
2. **字段被忽略不会报错。** 升级后要专门花时间找「哪些字段白写了」。
3. **迁移靠脚本自查，不靠眼。** 写一个比语义的脚本，比通读两遍配置可靠得多。
4. **查不到的 ID，明确标成假设。** 按同代模型对齐可以，但别把推断写成事实。

## 素材缺口

- provider 段的结构性改动是否需要重启才生效，**未验证**：文档只写了热重载覆盖 agents / commands / skills / MCP / plugins，没提 providers。
- 200k / 32k 这个兜底值的出处，素材只说是「V2 兜底」，没有链接。
- 「压缩点提前约 5 倍」是比值，实际压缩发生在第几条消息、多少字，没记录。
- 同族里有一个模型仍是 200000 / 20000，与同族 1M / 128k 不一致，当时没动，也没结论。
